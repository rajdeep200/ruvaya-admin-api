# Ruvaya Admin/API Implementation Audit

Audit date: 2026-07-31 (Asia/Kolkata). Primary repository: `ruvaya-admin-api`. Contract repository: sibling `ruvaya-storefront`.

## 1. Executive Summary

**Overall completion: 38%.** This percentage weights working behavior, persistence, security, contract compatibility, operational recovery, and usable admin workflows—not route-file count.

| Verdict area | Verdict | Basis |
|---|---|---|
| Production readiness | **NOT READY** | Critical CORS/inventory issues, incomplete integrations and admin workflows, and no database/provider runtime verification. |
| Storefront integration | **NOT READY** | Active runtime did not emit CORS headers; product media DTOs fail the storefront schema; seeded homepage/config are invalid. |
| Cashfree | **NOT READY** | Real adapter is called, but sandbox is untested and payment/inventory/idempotency/reconciliation behavior is incomplete. |
| Cloudinary | **NOT READY** | Only signature generation exists; confirmation, validation, persistence, deletion, and admin upload UI do not. |
| Security | **NOT READY** | Authentication core is credible, but the intended proxy controls are inactive, rate limiting is incomplete, and multiple public order/payment operations use raw internal IDs without capability protection. |
| Data integrity | **NOT READY** | Schema/migration match and paise storage are good, but checkout reservation predicates, webhook fulfilment, coupon redemption, retry and refunds have race/idempotency gaps. |

Finding totals: **4 critical, 16 high, 15 medium, 7 low**.

## 6. Database Findings

- **PASS:** Model coverage is broad and relationships are generally explicit (`schema.prisma:67-932`). Unique order number, SKU, slug, provider IDs, webhook IDs and refund idempotency keys exist.
- **PASS:** Money fields are integers in paise. Order items preserve price snapshots.
- **PASS:** Initial migration exactly corresponds to the current formatted schema.
- **PARTIAL:** Many entities lack useful query indexes: payment webhook processing by received/processed state, refund reconciliation, orders by customer/date, reviews by moderation state independent of product, analytics by session/date and source orders by status.
- **FAIL:** No database check constraints enforce non-negative stock/money/rating, `reservedStock <= currentStock`, sale price below regular price, or campaign end after start. Application checks do not cover every write path.
- **FAIL:** `ReviewToken.orderItemId`, analytics `orderId/campaignId`, daily metric foreign IDs and campaign attribution IDs are plain strings rather than foreign keys, permitting orphans.
- **PARTIAL:** Product soft deletion exists; many CMS/campaign/media deletion paths do not have consistent archival/version semantics.
- **PASS:** Seed password comes from environment and is Argon2id-hashed; no fake reviews are seeded.
- **FAIL:** Seeded storefront config/homepage are not contract-valid, and content pages lack initial versions (`prisma/seed.ts:5`).
- **NOT TESTABLE:** Migration apply, seed execution, database constraints and transaction behavior against PostgreSQL.

## 7. Cashfree Findings

### Adapter implementation

**PARTIAL.** Correct sandbox/live bases, headers and 2025-01-01 default are present (`src/lib/cashfree/client.ts:2-8`). Missing: timeout/AbortSignal, Get Payments, refund status, structured provider error categories, retry policy and safe persisted response redaction.

### Checkout integration

**PARTIAL.** Checkout calls Create Order (`orders/service.ts:228-257`). The provider call occurs after the database transaction; a timeout after provider creation but before local `Payment` creation leaves an unrecoverable order. Provider idempotency uses a fresh random UUID rather than stable checkout idempotency (`line 241`).

### Webhook

**PARTIAL.** Raw-body HMAC and constant-time compare are correct in design. Events are uniquely persisted. However success does not create a `PaymentAttempt`, consume/release reservation, decrement stock, queue notification or guard against out-of-order terminal events. A later FAILED event can change the Payment from SUCCESS to FAILED while Order remains PAID.

### Payment verification

**PARTIAL.** `getCashfreeOrder` can promote CREATED/PENDING to SUCCESS (`orders/service.ts:281-297`), but it does not add order history, consume inventory or verify currency/amount during polling.

### Retry

**FAIL.** Retry accepts a raw internal order ID without a secure token, has no idempotency key, and makes a new provider order on every call (`orders/service.ts:328-370`).

### Refunds

**PARTIAL.** Real refund API is called and over-refund is checked. Concurrency can pass the pre-check twice; provider response status is trusted without later verification; no refund status/ARN/reconciliation/timeline/notification exists.

### Sandbox verification

**NOT TESTABLE.** No Cashfree credentials were configured. Code correctly reports `NOT_CONFIGURED`; no success was faked.

## 10. Security Findings

### Critical

1. **Inactive proxy breaks cross-origin storefront access and intended controls.** Runtime headers prove `proxy.ts` was not applied. Separate-origin storefront API calls will fail CORS; CSRF origin enforcement and secure headers are also absent.
2. **Inventory lifecycle can oversell/corrupt stock.** Reservation predicate ignores existing reservations and paid processing never consumes stock/reservations.
3. **Checkout idempotency does not bind key to payload.** Missing header is accepted and same key/different payload reuses another request's order/session.
4. **Seed/public DTO contract failures block real storefront mode.** Empty homepage/config and missing image IDs deterministically fail the storefront's Zod schemas.

### High

- Raw internal order IDs authorize payment status and retry; retry can create unlimited provider sessions.
- Cashfree timeout/recovery and stable provider idempotency are absent.
- Out-of-order webhooks can regress payment state; attempts/inventory are not processed.
- Refund concurrency and reconciliation are unsafe.
- Cloudinary completion/validation/deletion are absent; arbitrary remote URLs are persisted (also an SSRF/content-origin governance risk).
- Unknown-email login and password-reset requests are not rate-limited.
- Password-reset delivery is absent.
- Per-role authorization is absent on direct admin Server Component data reads.
- Review images are silently ignored; public review submission has no rate limit.
- Analytics endpoint is unrate-limited, non-deduplicating and accepts arbitrary event names.
- CMS accepts arbitrary unsanitized JSON and publishes invalid references/content.
- Notifications are not implemented.
- No lockfile/reproducible install.
- No runtime database migration/seed verification.
- Product/admin completeness is materially below documentation claims.
- Coupon usage/redemption controls are not implemented.

### Medium

- Most business logic is embedded in route handlers rather than services.
- Many sensitive mutations lack audit records; audit IP/user-agent/request ID are not populated.
- CSP and HSTS are absent; intended basic headers are inactive.
- Public track/support/newsletter/search endpoints lack rate limits.
- Order tracking tokens never expire.
- Order numbers include `Math.random()` and time; uniqueness is DB-enforced but generation can collide and retry is not handled.
- Public APIs use hardcoded Cloudinary demo fallbacks.
- Admin pages have almost no filters, search, pagination or action confirmations.
- No loading/error boundaries or unsaved-change protection.
- CSV exports omit types/filters and silently cap at 5,000 rows.
- Content rich/structured data has no sanitization boundary.
- Prisma error mapping can expose generic 500s for normal conflicts.
- Source/Meesho model and workflows are insufficient.
- Analytics queries/definitions are operationally weak.
- OpenAPI is skeletal and inaccurate by omission.
- Documentation overstates implementation.

### Low

- Prisma seed configuration in `package.json` is deprecated for Prisma 7.
- Several source files are compressed to one line, harming reviewability.
- `pino`, `jose`, `recharts`, and `clsx` are installed but key promised structured logging/chart behavior is absent or unused.
- Currency formatting and server-rendered dates do not consistently apply configured store timezone.
- Admin navigation is not collapsible and has no active state/breadcrumbs.
- Some error messages do not explain saved/retry state.
- No Git repository metadata exists for auditability.

## 13. Critical Blockers

1. Move/activate the Next.js proxy and prove CORS from `https://ruvaya.in`, secure headers and mutation-origin handling.
2. Make every public DTO parse with the storefront's real Zod schemas; seed contract-valid published config/homepage data.
3. Repair inventory reservation predicates and implement expiry, release, consumption and stock decrement atomically with payment state.
4. Implement payload-bound checkout idempotency and recoverable Cashfree creation.

Until all four are resolved, switching the storefront from mock API or accepting customer orders is unsafe.
